# Axon — Contributor Orientation

Axon is a self-hosted personal agent for Matrix: a persistent state layer (sync, E2EE decryption, search, media proxy) that sits between a user's homeserver(s) and their clients. Arbitrary clients consume it through a stable, versioned HTTP + WebSocket API at `/v1/`. See `docs/mvp/prd.md` for the full product description.

## Key conventions

- **One human per Axon process.** N Matrix accounts inside, every account-scoped table carries `account_id`.
- **Clients:** client apps live under `clients/`. Follow any subtree `AGENTS.md` there; `clients/tui/AGENTS.md` covers axon-tui-specific conventions.
- **Sync:** Simplified Sliding Sync (MSC4186) only. No legacy `/sync`.
- **Event schema:** hybrid hot-columns + JSONB. `origin_ts` is `BIGINT` milliseconds since Unix epoch.
- **Provenance:** every event row has `provenance = 'upstream_homeserver'` for MVP.
- **API:** all routes under `/v1/`. WebSocket at `/v1/ws`. Envelope `{type, account_id, payload}`.
- **Migrations:** under `crates/axon-store/migrations/`, UTC timestamp prefixes (`YYYYMMDDHHMMSS_description.sql`, via `sqlx migrate add`) to avoid cross-branch collisions; forward-only — see ADR 0004. For any table that carries `updated_at TIMESTAMPTZ`, add a `BEFORE UPDATE` trigger (using a shared `trigger_set_updated_at()` plpgsql function) so application queries never need to remember `updated_at = now()` — the DB enforces it automatically.
- **A migration that has landed on `main` is immutable — never edit it, not even a comment.** sqlx checksums each migration file's *entire contents* into `_sqlx_migrations` and refuses to start when the bytes no longer match, so a comment-only or whitespace edit is a hard startup failure (`migration <version> was previously applied but has been modified`) on every database that already applied it — including every deployed instance, which is exactly who never re-reads the file. To change schema, add a new timestamped migration; to correct or expand a comment, say it in the new migration that supersedes it rather than editing the old one. `scripts/check-migrations-immutable.sh` enforces this. It runs in CI from `migrations-immutable.yml`, which is `pull_request`-triggered on purpose: only that event supplies the canonical base (`base.sha`) without a credential the fork doesn't have. It also runs from `.githooks/pre-push`, which covers branch pushes before a PR exists. It compares against the **canonical** `main` — not your fork's, which lags, so `git fetch upstream main` before trusting a clean local result — and only attributes changes made by commits this branch adds, so inheriting a migration change from `main` is never reported as yours. Only files that already exist on that base count as published — a migration your own branch adds is not in anyone's database yet, so amending it in a follow-up commit before the PR merges is fine. It also checks uncommitted work, so you can run it by hand at any point. A commit that must change a published migration anyway (reverting a bad edit back to the bytes deployments already applied, as `#375` did) declares itself with a `Migration-edit-approved: <reason>` trailer in its message; the check then reports the change and passes, and the PR should justify it. If a database is already broken this way, `axon db repair-migrations --apply` (`--features dev-tools`, README §Troubleshooting) rewrites the metadata for a checksum-only drift.
- **ADRs:** under `docs/adr/`, monotonic `NNNN-kebab-title.md`. Numbers collide across branches just like migrations do — before claiming the next number, check the open branches/PRs (`git ls-tree -r origin/<branch> docs/adr/`, or scan the open PRs), not just `main`. If two land on the same number, the later-merged one renumbers.
- **Errors:** `thiserror` in libraries; `anyhow` only at the `axon-server` binary boundary.
- **Logging:** `tracing` with structured fields — always include `account_id`, `room_id`, `event_id` where applicable. Logging and debugging support should always be considered as part of the design of new features or functionality. Before finalizing a new or modified feature, consider whether there is adequate logging and also whether any "developer mode" configurable option should be added to allow debugging in the future.
- **OpenAPI:** the spec is the source of truth. Handler types must compile against it (utoipa). Drift between spec and generated stubs is a bug.
- **Component separation:** the code is separated into three silos: `crates/` (server-side infrastructure), `clients/` (client-side infrastructure), and `smoke/` (testing infrastructure). Commits and pull requests should **not** change multiple silos at once. Each PR should be limited to its own silo. Files can be added to `docs/` combined with other silos where they are directly related to the change in that silo. The user can override this rule, but the agent should never do this on its own.
- **`axon-crypto` stays a stub.** Verification and all crypto-adjacent logic live in `axon-sync` — the engine can't be thin, it needs `ClientManager`, the per-identity locks, and supervision (ADR 0027). Do not add logic to `axon-crypto`; it remains a reserved stub.
- **Pull requests:** every PR body includes, by default, a **Verification guide** (prereqs + copy-pasteable, end-to-end steps that exercise real behavior — not just `cargo check`) and a **Code review guide** (a suggested file-by-file review order, dependencies first, plus a "where to keep a close eye" section calling out correctness, security, and lifetime concerns). Match the format of PRs #6 and #7. Scope both guides to the PR's actual diff. Subsequent changes to code in PR's should be impelmented as additional commits and pushes so that responsive comments can identify the precise commit that addresses the issue. Generally, the commits in a PR will all be squashed at merge time, subject to developer approval.
- **Pushes:** we normally do not push anything directly to `main`. Code is incorpoarted into `main` when PRs are merged. Any exception should be approved by a developer.git force-push should only be used to fix an error in branch history and not without developer approval.
- **Stacked PRs and branch deletion:** GitHub **silently closes** any open PR whose *base* branch is deleted out-of-band (`git push --delete`, `jj git push --deleted`, remote pruning). Only deleting the branch through GitHub's own "Delete branch" button on the merged PR retargets stacked children to the merged PR's base instead of closing them. So: before deleting a merged PR's branch, check for open PRs based on it (`gh pr list --base <branch>`) and either retarget them first (`gh pr edit <n> --base main`) or delete the branch via the GitHub UI. This has already cost us real work once — a feature PR was auto-closed this way and went unnoticed until live testing rediscovered the gap it addressed — so treat a nonzero `gh pr list --base` result as a hard stop.
- **Restack dependent PRs when a base changes shared files.** When a base PR's review fixes touch files a stacked child also edits, rebase the child and resolve conflicts immediately — don't leave reviewers staring at GitHub's conflict state.
- **`#N` is a GitHub autolink — never use it for anything else.** GitHub renders `#<number>` (in PR/issue bodies, comments, and commit messages) as a link to the issue or pull request with that number. Only write `#` immediately before a number when you mean a link to that exact, existing issue or PR. For every other numbered thing — review-comment indices, milestone phases, list items, ordinals, counts, versions — omit the `#` (write "comment 4", "step 3", "milestone 7a", "v2") so prose never sprouts bogus cross-links to unrelated issues.
- **Robustness at boundaries.** Every place axon crosses a network or process boundary — a client calling `/v1/`, axon-server calling a homeserver, the TUI calling axon — is a "what could go wrong?" checkpoint. Before merging code that crosses one, account for: (1) **Timeouts** — every outbound call gets one; never `await` a remote unbounded. (2) **Bounded resources** — a fixed pool (workers, connections, semaphore permits) must be paired with timeouts and/or cancellation, so one slow/hung peer can't permanently consume it. (3) **Hostile input** — validate size and shape *before* allocating from it; cap bodies/images/list lengths; never size a buffer or allocation directly from a number the peer controls. (4) **Concurrency** — name the shared mutable state and the lock/owner guarding it (the cold-connect gate vs. live-task severing in 7a is the model), and state which lost-update/reconnect race is closed and how. (5) **Partial failure** — one account/room/event failing is logged and skipped, never fatal to the loop (the established "best-effort, never fatal to sync" philosophy).
- **Secrets never reach logs, errors, or disk.** No log line, error message, or file may contain a password, access token, recovery key, or bearer token. The one sanctioned exception is a value the *developer* explicitly surfaces for the end user to consume once — `axon token issue` printing the raw bearer token to stdout, or `axon init` emitting a generated secret — and even then only at the moment of issue, never re-logged afterward. Secret-bearing inputs (login password, 4S recovery key) are consumed once and dropped, never persisted (ADR 0008, 0026).
- **Crash-safe multistep flows.** Axon or a client can be killed, crash, or lose power at any point in a non-atomic flow. Any multistep flow must leave the system in a state it can reconcile on the next boot — never a wedged resting state that can't recover on resume. The `deleting` teardown breadcrumb + boot reconcile (7a-4) and the transactional `search_outbox` (9a) are the models: write a durable intent, make the completion idempotent, heal on resume.
- **No duplicate code.** Before landing duplicate or near-duplicate logic, extract a shared helper or refactor. Duplicated implementations drift apart, and each copy becomes a place a fix can be forgotten — the shared `TIMELINE_SELECT` projection, the config-discovery rules, and the TUI parsers are all single-source-of-truth for exactly this reason.
- **Docs track code.** A change to behavior that end-user docs (`README.md`) or agent instructions (`AGENTS.md`, subtree `AGENTS.md`s) describe must update those docs in the same PR — they must reflect the project's state once the PR merges. Stale docs are a review finding.
- **OSS Rust conventions + simple dependencies.** Follow idiomatic open-source Rust unless there's a specific reason to deviate. Keep the dependency graph simple and prefer indirection (a consumer-owned port + composition-root adapter, ADR 0021) over tight coupling. When an ADR justifies a dependency choice against an alternative already in the graph, explain the *behavioral* difference, not just a library preference.
- **What not to build:** no push (APNs/FCM), no admin API, no multi-human-per-process, no federation, no S3 media backend — see `docs/mvp/implementation.md` "What not to build" for the full list.
- **Spelling:** U.S. English throughout all source files, comments, and docs (e.g. "initialize" not "initialise", "honors" not "honours"). Note that the Matrix spec itself uses some Britishisms (`m.tag` `favourite`), in which case the standard should be used in code.
- **Version control:** some developers who contribute to this repo use [jj (Jujutsu)](https://github.com/jj-vcs/jj) in colocated mode alongside git (both `.jj/` and `.git/` are present). *If the developer has jj in their local environment*, prefer jj commands for committing and branching; git commands still work but are not the primary workflow. Key operations:
  - Commit message: `jj describe -m "..."`  
  - New commit on top of current: `jj new`  
  - New commit off a specific base: `jj new <bookmark>@origin`  
  - Switch working copy: `jj edit <change-id>`  
  - Create/move a branch bookmark: `jj bookmark create <name> -r @` / `jj bookmark set <name> -r @`  
  - Push: `jj git push --bookmark <name>`  
  - Restack after base moves: `jj rebase -d <base-bookmark>` then re-push  
  - PRs are still opened with `gh pr create --base <base> --head <branch>`; `gh`'s "uncommitted changes" warning in colocated mode can be ignored as long as the bookmark was pushed correctly.
- **Pre-push web hook (optional but recommended).** CI (`web-lint-and-test.yml`) runs generated-schema drift detection, lint, formatting, tests, and build for `clients/web`. To catch those failures before CI, the repo ships a shared `.pre-commit-config.yaml` that runs the same web checks at push time when web-relevant files change. It requires the [`pre-commit`](https://pre-commit.com) runner (`pipx install pre-commit`, `uv tool install pre-commit`, `pip install --user pre-commit`, or `sudo apt install pre-commit`) and the normal `clients/web` pnpm dependencies (`pnpm install --frozen-lockfile` in `clients/web`). Enable it once per clone:
  - **git users:** `pre-commit install --hook-type pre-push` — fires natively on `git push`.
  - **jj users:** git hooks don't fire under jj, so push through the `jj-hooks` tool (`cargo install jj-hooks`) instead: `jj-hooks --runner pre-commit push`. To make `jj push` do that by default, add this alias to `~/.config/jj/config.toml`:

    ```toml
    [aliases]
    push = ["util", "exec", "--", "jj-hooks", "--runner", "pre-commit", "push"]
    ```

    Use `jj push`, not `jj git push`; direct `jj git push` bypasses the alias.

  Both front-ends read the same `.pre-commit-config.yaml`; only the driver differs. On a failure, run the command printed by the hook (for example `pnpm --dir clients/web format` for formatting, or `pnpm --dir clients/web gen:api` for schema drift) and push again. CI remains the backstop for anyone who skips the hook.
- **Web verification uses the package scripts.** For `clients/web` code
  changes, the local gate is `pnpm --dir clients/web lint`,
  `pnpm --dir clients/web test`, and `pnpm --dir clients/web build`. Do not
  use plain `tsc --noEmit` as a substitute for the build typecheck: the web
  package's root `tsconfig.json` is a project-reference file with no direct
  inputs, so plain `tsc --noEmit` can check zero app files. Use
  `pnpm --dir clients/web build` (or, for TypeScript only,
  `pnpm --dir clients/web exec tsc -b`) so the referenced app/node projects are
  checked.

Full conventions are in `docs/mvp/implementation.md` under "Conventions."

## Bootstrap and configuration

`axon init` (M13, ADR 0051) is the first-run bootstrap — it owns starter-config generation, secret generation, and local-service setup. Config precedence and discovery are described in the Milestone 2 notes below (figment: defaults < TOML < `DATABASE_URL` < `AXON_`-prefixed env).

- **Bootstrap has one owner.** `axon init` owns config/secret generation and first-run setup; helper and launcher scripts must not reimplement it. Scripts stay as source-checkout developer scaffolding.
- **Shell scripts must not reimplement config precedence.** Anything that exports `AXON_*` outranks the TOML file and can silently clobber user/platform config. Prefer the Rust config APIs over shell/PowerShell copies of the discovery rules.
- **Explicit config paths are promises.** `--config <path>` and `AXON_CONFIG=<path>` must fail loudly when the file is missing. Silent absence is acceptable *only* for convention-based discovery (`./axon.toml`, the platform config dir).
- **"No config found" ≠ "config is broken."** First-run prompts fire only when no config file exists *and* no config env is set. A parse error, a missing explicit path, or invalid env must fail with the real error, never silently drop into first-run.
- **Launcher behavior stays boring.** A run/launcher script does root-relative paths, `.env` loading, Cargo invocation, and optional dev Postgres — nothing more. No secret generation, config-file writing, or storage-location overrides unless the script's stated purpose *is* bootstrap.
- **Fallbacks that look like data loss must be observable.** If platform data/config/cache dirs can't be resolved and axon falls back to CWD-relative paths (ADR 0050), log a warning — a silent fallback hides where state landed.

## Testing and documentation

- **Isolate platform-default state in tests and docs.** Any integration test, smoke guide, or manual repro that expects throwaway state must set `AXON_SYNC__DATA_DIR`, `AXON_SEARCH__INDEX_PATH`, and `AXON_MEDIA__CACHE_DIR` explicitly — otherwise it reads and writes the real platform dirs (ADR 0050) and leaks state between runs.
- **Document config.** Each silo must have documentation of configuration and examples. For the server, README.md should list the most common config options, and .env.example should include examples of every option that can be set via environmental variables. Update these files when config options are added or changed.

## Design guardrails

Recurring failure modes distilled from M1–M13 review. They apply across crates and clients.

1. **Encode invariants in types, not comments.** Shared mutable state guarded only by a doc-comment is a latent bug — make the type system enforce it (the 7a per-identity lock and run-scoped verification tokens are the model, ADR 0022 / 0027).
2. **Store the key next to shared-but-partitioned state.** Whenever there is one physical slot with N logical owners, keep the owner's key beside the value — *or* flush/commit the slot on every key change. A single global slot keyed by "current context" silently drops concurrent work when the context switches mid-operation (the PR 192 draft-compose case: a per-room compose buffer and its pending queue must carry the room key or flush on room switch, never live in one "current room" slot).
3. **Bracket every borrow of shared state.** A borrow should be save-on-enter / restore-on-exit — ideally structurally via a scope guard, not by remembering to add restore calls at each exit path.
4. **Never infer intent from an incidental value shape.** When multiple code paths can produce the same value, that value can't carry semantics on its own — use explicit sentinels (the `search_outbox` account-purge sentinel, 9a), not shape-guessing.
5. **Reconciliation must handle absence, not just presence.** Prune-on-reconcile is half the job of any lossy / eventually-consistent sync; a reconcile that only adds and never removes is incomplete (the deferred config-drop half of #24, ADR 0024).
6. **In a single-threaded loop, fan out independent I/O.** Don't serialize independent remote calls behind one another when they could run concurrently.
7. **User-entered text must survive a failed mutation.** Any operation built from typed input (send, edit, draft) must leave that input recoverable when the call fails — a retryable local echo, a restored composer, a preserved buffer — never error-banner-and-gone. (The web client's sends have retryable echoes but a failed edit silently discarded the user's text — WCR-10 in `docs/reviews/2026-07-web-client-review.md`.) The one exception stays: secret-bearing inputs are consumed once by design, per the secrets rule above.
8. **Every view of server state declares its freshness story.** A client store or panel that displays server data must answer, at design time: which live frames update it, what happens on reconnect, or why staleness is acceptable. "Fetched once on mount" is a decision to document, not a default to fall into — the client-side counterpart of guardrail 5's "reconciliation must handle absence". (From WCR-06/08: the web thread panel and room list each silently opted out of ADR 0061's subscribe + gap-fill pattern.)

**When implementing a new feature:**

- A feature that touches shared state implicitly interacts with *every* existing path that touches that state. The audit surface is all readers/writers of the shared field, not just the diff.
- Test the transitions, not just the core operation. Boundaries and state transitions are where invariants break.

## Instructions after making changes

- Make sure to run `cargo fmt` on the code you modified after finishing making changes; limit the scope to the code you changed
- Make sure to fix any clippy issues `cargo clippy` on the code you modified after making changes
- Don't ignore any linting warning or add comments like "#[allow(clippy::too_many_arguments)]". The user can override a clippy warning but the agent should not do so on its own.
- **A docs-only commit may skip the full pre-push gate.** If a commit changes *only* documentation (`docs/`, `AGENTS.md`, `CLAUDE.md`, `README.md`, subtree `AGENTS.md`s — and no source, config, migration, workflow, or CI file), the fmt/clippy/test gate exercises nothing in the diff, so pushing past the hook (`git push --no-verify`) is acceptable. Any commit that touches code stays subject to the full gate below.
- More complete formatting and clippy checks can run before committing/pushing
**The repo is public, so GitHub-hosted runners (`ubuntu-latest`, `windows-latest`, `macos-latest`) get free, unlimited standard-runner minutes — CI is no longer restricted to self-hosted runners for automatic triggers.** `lint-and-clippy.yml`, `cross-build.yml`, and `publish-images.yml` trigger automatically on push/tag; workflows stay `workflow_dispatch`-only only where that's the right call for other reasons (e.g. expensive/manual smoke or integration runs), not because of a minutes budget. The local hooks are still the safety net for anything that isn't covered by an automatic run. Before pushing, either install the tracked hooks once per clone with `./scripts/setup-hooks.sh` (sets `core.hooksPath = .githooks`; `.githooks/pre-push` runs the full gate), or, if you haven't, run it by hand:

```bash
cargo fmt --all -- --check
cargo clippy --all-features --all-targets -- -D warnings
cargo test --all
```

Smoke gates are manual because they may require Docker and a true-local Synapse
stack. Use `scripts/smoke-gate.sh <mode>` before pushing component changes that
cross process/network boundaries:

| Changed area | Smoke gate |
|---|---|
| `smoke/tui` or terminal rendering in `clients/tui` | `scripts/smoke-gate.sh tui` |
| TUI changes that depend on real Axon/local-stack behavior | `scripts/smoke-gate.sh tui-true-local` |
| `smoke/server`, `crates/axon-server`, `crates/axon-api`, `crates/axon-sync`, or `crates/axon-store` API/sync behavior | `scripts/smoke-gate.sh server` |
| `smoke/local-stack` or shared smoke harness behavior | `scripts/smoke-gate.sh all` |

The pre-push hook does not run Docker-backed smoke by default. Opt in with
`RUN_SMOKE=tui`, `RUN_SMOKE=server`, `RUN_SMOKE=tui-true-local`, or
`RUN_SMOKE=all`.

- **M18 — live-event ephemeral passthrough (ADR 0056, backend PR).** `LiveFrame::Ephemeral` fans out an allowlisted raw ephemeral event (`m.typing`, `m.receipt`) verbatim as an `ephemeral.passthrough` `/v1/ws` frame — the generic escape hatch for the room-scoped ephemeral long tail the homeserver delivers via sync but axon previously dropped (typing, receipts, unread counts), so a future *room-scoped* signal reaches clients via config alone rather than a bespoke `LiveFrame` variant touching all four crates. Server-only, single PR. `axon-sync` registers one plain `add_event_handler(forward_ephemeral_event)` in `run_account` (no child task — matrix-sdk dispatches `AnySyncEphemeralRoomEvent` through the ordinary per-room handler path, same as room state, via `Raw<AnySyncEphemeralRoomEvent>` so the SDK only captures the raw bytes rather than fully deserializing a discarded typed event) that checks the raw event's size against a `EPHEMERAL_EVENT_MAX_BYTES` cap (256 KiB, mirroring `RELATION_READ_CAP`/`REACTION_AGG_PAIR_CAP` — the shared live-event bus fans out to every account's `/v1/ws` clients, so an oversized EDU from one account's homeserver must not cost every other account ring-buffer space), parses the raw JSON via a `parse_raw_json` helper shared with the `persist_*` handlers, checks the event `type` against the new `sync.ephemeral_event_types` allowlist (default `["m.typing", "m.receipt"]`, fails closed, config-extensible, allowlist misses logged at debug), and forwards `{account_id, room_id, event_type, content}` unmodified — nothing is persisted, since ephemeral events mutate no store row. **Deliberately minimal**: no typing-frame coalescing and no separate ephemeral lag domain, both considered and deferred until lag is actually measured (the ADR lists them as mitigations, not requirements). `m.presence` stays off the default allowlist and, unlike other future room-scoped EDUs, **cannot** be enabled by config alone even once the lag question is settled: presence is account-scoped and dispatches through a structurally different matrix-sdk handler kind (`HandlerKind::Presence`, no `Room` argument) that `forward_ephemeral_event` never receives — forwarding it needs a second handler registration, not just an allowlist edit. `run_account` logs a boot warning if `m.presence` is configured anyway, so this doesn't fail silently. The frame shape (`room_id: Option<String>`) still accommodates presence's eventual wire shape once that handler exists. Considered and rejected giving `m.typing` a bespoke typed frame/route (to pre-resolve display names or self-filter server-side): `axon-tui` already caches room members for message rendering, so that work is either trivial client-side code or something the client does anyway, while a bespoke frame would add a `room_state` read to what's otherwise a zero-I/O forward and undercut the ADR's whole point on its first use case. No outbound route exists (or is planned here) for a client to *send* its own typing/receipt state to the homeserver — that's separate work symmetric to issue #130. Client consumer (`axon-tui` typing indicator + read receipts) is a separate follow-up PR per the one-silo-per-PR rule.
- **M19 — Matrix C-S verb batching (design; ADR 0068).** Proposed: closes the remaining Matrix C-S parity gaps inventoried in issue #279 (room-membership verbs, room settings, account/profile actions) by stamping ADR 0021's consumer-owned-port + composition-root-adapter pattern once per trait group rather than once per verb, reusing `SdkGateway`'s existing room-resolution and error-mapping helpers verbatim. Planned as a 6-PR sequence: **M19a** typing notice (piggybacks on the already-designed #278/ADR 0067 read-receipt relay, no new ADR) → **M19b** existing-room membership (leave/forget/invite/kick/ban/unban, via `SdkGateway::room()`) → **M19c** room entry (join/knock/create, via `ClientManager::get_or_connect` directly — split from M19b for its bigger test surface: M10 backfill pickup, DM/encryption flags) → **M19d** room settings (name/topic/avatar/tags, one route per field) → **M19e** power levels, split out alone because a bad write can permanently strand the account below the PL needed to self-correct, and the PR must decide an explicit guardrail before shipping → **M19f** account actions (profile/ignore/directory search). Tier-C gaps needing real design work are tracked separately, not part of M19: invited-room visibility (no stripped-state handling anywhere in `axon-sync`/`axon-store` today — recommended as the next milestone after M19, since it's the precondition for M19b's `invite` being useful in reverse); presence (stays deferred per ADR 0056, no new ADR until the lag question is actually addressed); and unread/notification counts (an independent per-room SDK summary mechanism — ADR 0068 corrects issue #279's own text, which mistakenly suggested folding this into #241's unrelated account-level sync-readiness signal). **M19a landed**, bundled with the read-receipt relay it piggybacks on (#278/ADR 0067) since neither had code yet: a new `EphemeralSender` port (`crates/axon-api/src/sender.rs`), split from `MessageSender` because these two sends are best-effort/fire-and-forget from the caller's perspective. `POST /v1/accounts/{account_id}/rooms/{room_id}/read` (body `{"event_id"}`) sets both the public read receipt and the private fully-read marker via `Room::send_multiple_receipts`; `PUT .../rooms/{room_id}/typing` (body `{"typing"}`) calls `Room::typing_notice`. Both resolve through `SdkGateway::room()` exactly like the M6 mutations. **M19b landed**: a new `MembershipSender` port (`crates/axon-api/src/sender.rs`), split from `MessageSender` for the same reason as `EphemeralSender` — none of these six calls return an event id the caller needs, since the resulting `m.room.member` state event round-trips through sync like any other state change. `POST .../rooms/{room_id}/{leave,forget}` take no body; `POST .../rooms/{room_id}/invite` takes `{"user_id"}`; `POST .../rooms/{room_id}/{kick,ban,unban}` take `{"user_id", "reason"?}`. All six resolve through `SdkGateway::room()` and call straight through to the matching `Room::{leave,forget,invite_user_by_id,kick_user,ban_user,unban_user}` method, except `forget`, which checks `Room::state()` up front and rejects a still-joined/invited room as a clean `400` rather than letting the SDK's `WrongRoomState` fall through `map_sdk_err`'s generic upstream-error catch-all. Each call is bounded by `sync.membership_mutation_timeout_secs` (default 15s, mirroring `ephemeral_send_timeout_secs`'s pattern) per the boundary-robustness guardrail above, and each handler logs a structured success/failure line with `account_id`, `room_id`, the target user where applicable, elapsed time, and the mapped error on failure, per ADR 0068's structured-logging requirement for M19 routes. **M19c landed**: a new `RoomEntrySender` port (`crates/axon-api/src/sender.rs`), split from `MembershipSender` because none of these four resolve through an existing `Room` — there is no room yet — so they go through `ClientManager::get_or_connect` directly rather than `SdkGateway::room()`, and because every method here returns the resulting room's id rather than `()`. `POST .../rooms/join` (body `{"room_id_or_alias", "server_names"?}`) calls `Client::join_room_by_id_or_alias`; `POST .../rooms/knock` (body `{"room_id_or_alias", "reason"?, "server_names"?}`) calls `Client::knock`; `POST .../rooms/dm` (body `{"user_id"}`) calls `Client::create_dm`, which — under the `e2e-encryption` feature `axon-sync` already enables — bundles `m.room.encryption` into the room's `initial_state` and attempts `mark_as_dm` internally; `POST .../rooms` (body: `name`/`topic`/`invite`/`is_direct`/`public`/`preset`/`encrypted`, all optional) calls `Client::create_room`, and when `encrypted: true`, `SdkGateway::build_create_room_request` puts the same `m.room.encryption` entry into `initial_state` before creation — `Room::enable_encryption()`'s post-hoc, racy path is never used. Both `create_room` and `create_dm` double-check `Room::is_direct()` after the SDK call and retry `mark_as_dm` explicitly (propagating any failure through Axon's own structured logging) if the SDK's internal attempt silently failed — the SDK only logs that failure via its own internal `error!` macro rather than surfacing it. Each call is bounded by `sync.room_entry_timeout_secs` (default 30s, longer than `membership_mutation_timeout_secs` since these can involve federation resolution), and each handler logs the same structured success/failure shape as M19b. **Known, accepted risk**: `create_room`/`create_dm` are not idempotent — Matrix's `createRoom` endpoint has no idempotency key, so a client retry after an Axon-side timeout can create a second room upstream if the first attempt actually succeeded after Axon's own client-side future was dropped; there is no protocol-level fix available at this layer, so this is documented rather than solved (see the doc comments on `SdkGateway::create_room`/`create_dm`). **M19d landed**: a new `RoomSettingsSender` port (`crates/axon-api/src/sender.rs`), split from `MembershipSender` because `set_tag`/`remove_tag` write **room account data** (`m.tag`, private to this account), not a state event, despite ADR 0068 grouping all four fields under one "room settings" batch — the other three (`name`/`topic`/`avatar`) do resolve through `SdkGateway::room()` exactly like M19b. `PUT .../rooms/{room_id}/name` (body `{"name"}`) calls `Room::set_name`; `PUT .../rooms/{room_id}/topic` (body `{"topic"}`) calls `Room::set_room_topic` — an empty string is the clear signal for both, since the SDK has no separate "remove" primitive for name/topic. `PUT .../rooms/{room_id}/avatar` (body `{"upload_id"}`) claims an already-staged upload (the same `StagedUploadService` flow `send_media` uses — Axon has no route that hands a client an `mxc://` URI to reference directly, and the `ClaimedUpload → MediaAttachment` mapping is shared with `send_media` via a `From<ClaimedUpload> for MediaAttachment` impl in `crate::uploads` rather than duplicated per handler) and calls `Room::upload_avatar`, which uploads the bytes and sets `m.room.avatar` in one call; `DELETE .../rooms/{room_id}/avatar` calls `Room::remove_avatar`. `set_name`/`set_topic`/`set_avatar`/`remove_avatar` all share a `SdkGateway::ensure_joined` guard (mirroring `forget`'s own state guard above) before touching the SDK: `send_state_event`/`upload_avatar` internally call `ensure_room_joined` and fail with an SDK-local `WrongRoomState` that `map_sdk_err` can't distinguish from an upstream failure, so a non-joined room now fails as a clean `400` instead of a misleading `502` for any of the four — an initial version of this PR only added the guard to `set_avatar`, missing that the other three hit the same SDK precondition; caught in review and generalized into one shared helper rather than three more copies of the same check. `set_avatar` additionally requires a declared `content_type` on the staged upload (rejecting a missing one rather than defaulting to `image/png`, since that default exists for message sends where any declared kind is fine, not for an avatar where the whole point is asserting it's actually an image). `PUT`/`DELETE .../rooms/{room_id}/tags/{tag}` (`PUT` body `{"order"?}`) call `Room::set_tag`/`remove_tag`, gated by a new `parse_tag_name` helper that accepts only `m.favourite`/`m.lowpriority`/`m.server_notice`/`u.`-prefixed custom tags of at most 255 bytes and rejects anything else as a clean `400` — `TagName`'s own `From<T: AsRef<str>>` conversion is infallible and would otherwise silently accept a made-up, non-namespaced tag. The custom-tag check delegates its prefix validation to ruma's own `UserTagName: FromStr` (picking up any future change to what ruma considers valid automatically) and layers two additional, deliberately stricter rules on top: a bare `u.` with no name after it is rejected (ruma's own parser alone would accept it), and the 255-byte cap bounds an otherwise-unbounded custom tag name (mirroring the upload-metadata caps in `axon-api::routes::uploads`) rather than letting an oversized one round-trip to a homeserver-dependent rejection. `order` is validated against the Matrix spec's documented `[0, 1]` range for `m.tag` (`validate_tag_order`) — ruma's own `TagInfo` carries it as a bare `Option<f64>` with no bound, so this closes the one input in the whole PR that otherwise skipped boundary validation before reaching the SDK. All six routes use `PUT`/`DELETE` rather than M19a/b/c's `POST`, since these are idempotent field-set/clear operations. Every non-avatar call reuses `sync.membership_mutation_timeout_secs` rather than a separate room-settings timeout — both are local-room state/account-data writes with no federation resolution, so there's no reason to tune them independently; avatar-set reuses `media.upstream_upload_timeout_secs` instead, since it does a real media upload like `send_media`. **M19e landed**: a new `PowerLevelsSender` port (`crates/axon-api/src/sender.rs`), split from `RoomSettingsSender` — unlike M19d's four fields, this is the one M19 verb where a client mistake isn't just a bad write but a potential permanent lockout: dropping your own resolved power level below what's needed to send another `m.room.power_levels` event succeeds at the protocol level (no `M_FORBIDDEN` for `map_sdk_err` to catch), leaving no way to self-correct. `PUT .../rooms/{room_id}/power_levels` (body: `ban`/`invite`/`kick`/`redact`/`events_default`/`state_default`/`users_default`, all optional, plus a `users` map of user id → level and an `acknowledge_self_demotion` flag) merges role-threshold and per-user changes into one in-memory `RoomPowerLevels` and sends exactly one `m.room.power_levels` state event — deliberately not matrix-sdk's own `apply_power_level_changes`/`update_power_levels`, which are two independent read-modify-send round trips and would fire two state events for one client request, letting the guardrail see a stale intermediate state between them. Before sending, `SdkGateway::check_self_demotion_guardrail` computes the caller's resolved level in the merged result via ruma's `RoomPowerLevels::for_user`/`for_state(StateEventType::RoomPowerLevels)` (the precise level required to send `m.room.power_levels`, not the `state_default`/`events_default` shorthand ADR 0068 used illustratively — an `events` override specifically for that event type is rare but spec-legal) and rejects the write as a clean `400` unless `acknowledge_self_demotion` is set. `GET .../rooms/{room_id}/power_levels` returns the same fully-resolved levels the write path computes internally — added because no generic Tier-2 state read exists yet (ADR 0055's proposal was never implemented), so without it no client could read a room's power levels through Axon at all. `set_power_levels` shares M19d's `ensure_joined` guard; both routes reuse `sync.membership_mutation_timeout_secs`, same reasoning as M19d's non-avatar calls. `room_name`/`room_avatar`/`room_topic` stay out of scope here, owned by M19d's dedicated routes. **M19f landed**: a new `AccountActionsSender` port (`crates/axon-api/src/sender.rs`) covering this account's own profile and ignore list, another user's profile, and public-room directory search — kept as one PR for the same reason M19b's six verbs were, since none of these seven routes resolve through a `Room` handle; every call goes through `ClientManager::get_or_connect` directly. `PUT .../accounts/{account_id}/profile/display_name` (body `{"display_name"}`) calls `Account::set_display_name`, with an empty string clearing it — the same convention as M19d's `set_name`/`set_topic` — issuing the SDK's real profile-field-delete call under the hood rather than writing an empty string to the homeserver. `PUT .../profile/avatar` (body `{"upload_id"}`) claims an already-staged upload and calls `Account::upload_avatar`, mirroring M19d's room-avatar upload+set shape (including the same "content type must be declared and be an image" validation); `DELETE .../profile/avatar` calls `Account::set_avatar_url(None)`. `GET .../users/{user_id}/profile` calls `Account::fetch_user_profile_of` and reads the typed `DisplayName`/`AvatarUrl` static profile fields off the response — a genuine read mixed into the same port as the mutations, the same shape M19e's `PowerLevelsSender` already has. `PUT`/`DELETE .../users/{user_id}/ignore` call `Account::ignore_user`/`unignore_user`; `ignore_user` rejects an attempt to ignore the account's own user id up front as a clean `400`, since the SDK's own guard (`Error::CantIgnoreLoggedInUser`) is a local precondition failure with no `client_api_error_kind` that `map_sdk_err`'s catch-all would otherwise surface as a misleading `502`. `GET .../directory/public_rooms` (query: `server`, `search_term`, `limit`, `since`, all optional) calls `Client::public_rooms_filtered` — the one M19f route ADR 0068 called out as needing its own request/response shape rather than the `{"data": {}}` empty-object envelope the other four share, since it's a paginated read, not a mutation. Non-obvious choices made in 7a (state machine — see ADR 0022; discovery — ADR 0023):

- **Homeserver discovery is server-side** (ADR 0023). `homeserver_url` is optional on login: omitted → axon resolves the MXID's server name via `.well-known/matrix/client` (fallback `https://<server name>`; candidates validated by scheme + a non-empty `/_matrix/client/versions`) in `axon-sync`'s `discovery` module, *before* the per-identity lock (which is keyed by the resolved URL). Clients never discover — two clients resolving the same user differently would mint duplicate accounts under the `(user_id, homeserver_url)` natural key. Supplied → the escape hatch for broken well-known and plain-HTTP loopback dev homeservers; it's normalized (trailing slash trimmed so it keys identically to a discovered URL) and scheme-checked (HTTPS unless loopback — a plain-HTTP public host is refused so the password can't leave in cleartext), but *not* probed (caller-asserted; a bad URL surfaces at SDK login). Discovery failures are `502` and touch nothing. A 2xx well-known whose body isn't JSON is treated as *absent* (fall back), not invalid — catch-all servers (Caddy/SPA/default-vhost) 200 every path with an empty/HTML body. On both paths the MXID's *domain* is then checked against the homeserver's declared server name (`/_matrix/key/v2/server`, best-effort): `@adam:matrix.example.org` — a common confusion — is a `400` did-you-mean naming `@adam:example.org`, never a misleading `401` and never a silent login as a different identity.

- **Explicit `accounts.state` (`active` / `deactivated` / `deleting`), orthogonal to a `verified` flag.** `active` syncs+sends; `deactivated` is a reversible pause that **retains all data** (logout / token loss); `deleting` is a *transient* teardown breadcrumb a later boot reconcile completes (deletion is a hard row removal, no resting tombstone). A separate `verified` bool caches whether axon's own device is cross-signed (re-derived from the SDK, not write-once; its derivation is stubbed to `false` until a later 7a PR). `state` is never set directly by a client — it's a consequence of the lifecycle verbs.
- **Connection gated on `state = active` at the single choke point.** `Store::list_accounts()` returns **only `active` rows** (the safe default the sync boot loop iterates); `ClientManager::get_or_connect` refuses a non-active account with `GatewayError::AccountNotActive` (→ `403`), so the lazy gateway send path is gated too. This is the **groundwork** for #24, not the whole fix: the gate is **cold-connect only** (an already-cached client isn't re-checked), so on its own it gives only "a non-active row gets no *new* client". Severing a *live* account is done actively by the lifecycle verbs: **`logout` (7a-3)** flips the row to `deactivated` *first* (so the gate refuses new connects), then cancels the account's supervised task **and awaits its drain** (per-account cancellation: a token + join-handle registry populated in `spawn_supervised` — cancellation is cooperative, and the task holds the SDK store dir until drained, so a re-login must not restage it earlier; an overrunning drain escalates to abort, and a task surviving even that fails the verb with the task left registered, which login refuses until a retry reaps it), then evicts its cached client (`ClientManager::take`, which serializes on the slot lock to close the reconnect race) and best-effort invalidates the device token upstream; `DELETE` (7a-4) reuses the same cancellation. 7a-4 (#61) added explicit account deletion, an interrupted-delete reconcile, and an orphan-store-dir GC (ADR 0024). **Config-based account provisioning has since been retired entirely** (closing #65, and with it the two-restart resurrection hole in #66): `SyncEngine::start` no longer touches `accounts` before spawning tasks, `AccountProvision`/`SyncConfig.account` are gone, and every account now comes from an explicit runtime call (`login` or the token-import verb below) — so `DELETE` is durable **by construction**, with no transitional guard left to carry. Wider views get their own explicitly-named accessor (never a shared "all rows" method that could misfire from the connect path): the read API uses `list_client_visible_accounts` (active + deactivated — a logged-out account stays discoverable for re-login; excludes transient `deleting`), and teardown reconcile / orphan GC add theirs in 7a-4.
- **`AccountState` is a Rust enum in `axon-store`** (re-exported), stored as `TEXT` + `CHECK` (matches the rest of the schema, not a PG `ENUM`); an unknown stored value is a column-decode error, not a silent default.
- **`recover` (7a-5, ADR 0026) was originally the boot-time `recover()` promoted to an on-demand verb; the boot path it was promoted from has since been retired along with config-based provisioning.** `POST /v1/accounts/{id}/recover` takes a 4S recovery key and runs the same single SDK call (`encryption().recovery().recover()`), then reuses `redecrypt::sweep_pending_utds` (bounded by `RECOVER_SWEEP_TIMEOUT` so the under-lock backfill can't starve a concurrent logout/delete) to back-fill the UTDs the imported keys now unlock. It requires an **`active`** account (it needs a live, authenticated client via `get_or_connect`): a `deactivated` row is a `409` (log in first), `deleting` a `409`, unknown id a `404`. Errors are classified, not blanket-400'd: only the SDK's `SecretStorage` failure (wrong/rotated key, or no Secure Backup) is a readable `400` (`LifecycleError::RecoveryFailed`, with a stable non-leaky message), never a silent permanent UTD; any other `RecoveryError` is a generic `500` (logged, not the caller's fault). Held under the same per-identity lock as login/logout/delete; the recovery-key string is consumed once and never persisted. Loopback-bound until 7b like the other secret-bearing verbs.
- **`POST /v1/accounts/import` (ADR 0024) adopts an existing `access_token` + `device_id`** — the runtime replacement for the retired `sync.account.access_token` config path (e.g. a token issued by another client, or an SSO-only account with no password). Same idempotency shape as `login` (new identity mints a row; `active` is a no-op; `deactivated` reactivates using its *stored* endpoint; `deleting` is a `409`), but `homeserver_url` is required (no MXID-based discovery for a bare token) and is consulted only when minting a new row. Unlike `login`, no homeserver call confirms the token up front — `restore_session` is purely local — so `AccountLifecycle::import_token` (`axon-sync`) validates it with a `whoami` round-trip before activating: a token belonging to a different user or device is rejected as `AuthFailed` (→ `401`), same as `login`'s rejected-credential case.
- **`verified` is now derived from the SDK, not stubbed `false` (ADR 0026).** The bool caches whether axon's own device is cross-signed, re-derived from `get_own_device().is_cross_signed_by_owner()` (the check the SDK uses internally — accurate immediately, unlike the `verification_state()` subscriber, which only refreshes on a `/keys/query` round-trip). It is **not write-once**: a per-account **verification watcher** child task in `run_account` (same child-token + drain lifecycle as the re-decryption queue) subscribes to `verification_state()` and re-derives+persists on every change (login, recover/verify, cross-signing rotation/reset). `recover` also persists it synchronously so an immediate read-back reflects the new state. Watcher and `recover` both write `verified` **under the same per-identity lock** (owned by `SyncEngine`, shared with every `AccountLifecycle` and watcher) so neither clobbers the other (lost-update race). `logout` resets `verified` to `false` as it deactivates, so a `deactivated` account reports `false` and a re-login (fresh, unverified device) can't read a stale `true`. `AccountDto.verified` stays `Option<bool>` on the wire (forward-compat) but is now always populated.
- **Interactive SAS verification (7a-6, ADR 0011) drives the matrix-rust-sdk SAS state machine in `axon-sync`.** `POST /v1/accounts/{id}/verify {device_id}` starts an emoji exchange against one of the user's trusted devices and returns a `flow_id`; `POST …/verify/{flow_id}/confirm` and `…/cancel` advance/end it (loopback-bound, like the other secret-/trust-bearing verbs); `GET …/verify` and `GET …/verify/{flow_id}` (open) read replayable per-flow state so a client that dropped its socket resumes without assuming the frames it missed. Live progress streams as `verification.{requested,sas,done,cancelled}` frames over `/v1/ws` (the `LiveFrame::Verification` arm of the now-widened live-event bus; peer-initiated requests surface as `verification.requested` with no HTTP kickoff, via an `m.key.verification.request` to-device handler each account's supervised task registers). **Flows are ephemeral and never persisted** — the SDK's in-flight SAS state isn't serializable, so a flow is re-readable across a *client* reconnect (this process up) but not across a process restart; an in-memory registry holds the live SDK objects (`get`/`list` re-derive emoji/decimals live), and a terminal flow's outcome is retained for a 5-min grace TTL (so a missed `cancelled` is still readable) then evicted lazily. Cross-signing is the *last* step, so any crash before it leaves the device merely unverified, never half-trusted. **`confirm` does not write `verified`** — the existing `watch_verification` watcher stays the single writer of that column (ADR 0026). The `VerificationEngine` lives in `axon-sync` (it needs `ClientManager`/locks/supervision); `axon-crypto` stays a stub. Adapted onto the API's `VerificationService` port by `axon-server`, same as the lifecycle port. **Boundary + contract decisions are recorded in ADR 0027** (raised in the PR 6 review): (a) verification lives in `axon-sync`, not the `axon-crypto` "thin verification surface" the layout originally named — the engine can't be thin (it needs connection/locks/supervision); (b) the operations contract is **HTTP-only** — no client→`/v1/ws` commands and **no explicit `accept` verb** (the protocol accept needs no human decision, so the driver accepts automatically; the spec's "equivalent WS commands" + client `accept` are deferred to 7b); (c) every started/accepted request advertises **SAS only** (`request_verification_with_methods`/`accept_with_methods` — the SDK default includes QR, deferred); (d) the incoming listener rejects anything that isn't `is_self_verification()` (M7a verifies axon's own device only); (e) `confirm` gates on the live SAS state (`can_be_presented`) so a too-early confirm can't return a false success, and distinguishes a done flow (idempotent ok) from a cancelled one (error); (f) verification drivers are **run-scoped** — cancelled on every supervised sync-run teardown via the flow registry, so a driver never outlives its evicted client — and `start` takes the **per-identity lifecycle lock** so it can't race login/logout/delete; (g) pre-7b, the read + `/v1/ws` surfaces stay open (trust-state disclosure accepted under the existing "not remotely deployable without 7b" constraint) and frames ride the lossy bus (clients must re-read `GET …/verify/{flow_id}` on reconnect — it's the source of truth). **Scope: this PR is the backend API only.** The PRD frames SAS as "a first-class account-lifecycle API (and `axon-tui` can drive them)" — the API is the 7a-6 deliverable; the `axon-tui` verify UI that consumes it is separate client work (alongside the M12 first-run flow), not part of this PR, so 7a-6 being landed does not mean an interactive verify UX is available end-to-end yet.

Non-obvious choices made in M10 (history backfill — see ADR 0043, ADR 0044):

- **Backfill is a continuous background task, not a boot sweep.** Spawned in `run_account` beside the re-decryption queue (child cancel token, drained on shutdown), it pages each incomplete joined room one page older, then idles and **re-polls `client.joined_rooms()`** (`sync.backfill_idle_poll_secs`) — which is how a newly joined / re-joined room is picked up without a restart, and why "joined rooms only" is safe. The instant window a room shows on first sync is still `sync.timeline_limit` (now only a cold-start knob); backfill extends history behind it.
- **Same ingestion path, minus the live emit.** Back-pagination (`Room::messages`) does *not* dispatch through `add_event_handler`, so the driver persists each paged `TimelineEvent` itself via `persist_event_core` (refactored out of the live handler) — hot columns, `upsert_event` (+ the M8/M9 `search_outbox` obligation), crypto siblings all apply. Backfilled events skip the `/v1/ws` emit (replaying deep history through the live bus would mislabel it as just-arrived); they reach clients via timeline reads + search instead.
- **Per-room resume cursor.** `room_backfill(account_id, room_id, oldest_seen_token, complete, events_backfilled)`: the resume token is the SDK `Messages.end`; a room is `complete` when `end` is `NULL`. Saved after each fully-persisted page, so a mid-page crash re-pages idempotently (`upsert_event` is `ON CONFLICT DO NOTHING`, so no duplicate rows *or* outbox obligations). `sync.backfill_target_depth = 0` (default) means "to room start"; a non-zero cap stops paging without marking complete (raising it later resumes).
- **Disk-space safety valve gates backfill only.** Backfill grows storage unbounded, so it pauses when free space on the sync data filesystem falls below `sync.backfill_min_free_bytes` / `_percent` (cheap `fs4::statvfs` before each page). Live sync is unaffected. A shared `BackfillHealth` handle (threaded like `index`) records paused + free-bytes; exposed at `GET /v1/status` (poll-based — a `backfill.paused/resumed` WS frame was deferred because the live bus is account-scoped but the disk signal is engine-global). Guards the local box; a split-Postgres deployment monitors the DB host separately.
- **Left-room search: filter by default, purge opt-in (ADR 0044).** `GET /v1/search` hydrates hits through `Store::get_event_if_joined`, which drops events in rooms the local user has left/been banned from — reusing `list_rooms`' `NOT EXISTS(m.room.member = leave/ban)` predicate (ADR 0037). Non-destructive and reversible (re-join restores). `sync.purge_on_leave` (default off) additionally makes a leave/ban trigger `Store::purge_room`: one atomic statement deletes the room's events (cascading siblings) + state + room account-data + backfill cursor and enqueues a **room-scoped** search purge (a `\u{1f}room\u{1f}<id>` outbox sentinel the writer applies via Tantivy `delete_query` on the `account_id` **and** `room_id` terms, so a shared room's other account is untouched).

Non-obvious choices made in 9a (search indexing engine — see ADR 0039):

- **Index from the resolved M8 projection, never the raw event.** The indexing unit is "(re)derive the document for `(account_id, event_id)`", resolved through the same `Store::get_event` projection the read API uses — so a message indexes its latest edited body and a redacted event is removed. The affected ids are the event's own **plus**, for a relation/redaction, its *target's* (the store computes this fan-out in the outbox statement). This makes indexing **order-independent** (the case M10 backfill produces, paging newest→oldest): an edit or redaction arriving before its target is a no-op until the target lands, then the target re-derives from the projection (which already folds the relation in). Standalone `m.replace`/`m.reaction` events are never their own document — their text belongs to the target.
- **A transactional outbox makes the index convergent (not best-effort).** Every index-affecting store write appends `search_outbox(seq, account_id, event_id)` in the *same statement* as the mutation (`upsert_event`, `update_decrypted_event`, `delete_account_row`, via `WITH … RETURNING`), so a change and its indexing obligation commit atomically. Entries are engine-neutral (an *affected id*, never a Tantivy doc); a re-decryption enqueues its own id (the only durable signal for an in-place `UPDATE` that mints no new `events.id`), and `event_id = ''` is the account-purge sentinel. The single actor owns the sole writer and **drains the outbox in `seq` order**, committing a batch then advancing a durable contiguous cursor (`search_meta.outbox_cursor`) and pruning. `axon-sync` only pokes it with a best-effort `IndexHandle::notify` wakeup hint — droppable *without consequence*, since the obligation is already on disk. This (replacing an earlier lossy `try_send` queue) is what converged the design in review.
- **`events` is the rebuild source; the outbox is the prunable delta.** On a **fresh** index (new/empty/schema-bumped directory — detected by an `axon_schema_version` sidecar checked *before* `open_or_create`, which would otherwise fail on a schema change) the actor **seeds** from `Store::events_for_index` (a keyset, projection-aware scan, one query per batch, throttled, as a background task so boot never blocks). Pruning the outbox is therefore always safe — it never holds the only copy needed to reconstruct a lost index. Enabling search *after* M10 backfill indexes the full corpus, since the seed reflects whatever is in `events`.
- **Account deletion is durable and search-disabled-safe.** `delete_account_row` appends the purge sentinel in the same statement that drops the row; `search_outbox` has **no FK** to `accounts`, so the obligation outlives the cascade — a crash, or a deletion while search is disabled, is healed on the next enabled drain. When the actor is live the lifecycle verb additionally `flush`es (drain-to-empty + ack) so the documents are gone before it returns (ADR 0024 ordering).
- **Keyword fields, not facets.** `account_id`/`room_id`/`sender` are exact-match `STRING` fields (robust to `!`/`:`/`@`/`/` in ids without facet-path escaping; `STRING | STORED` doubles as the hydration field), a deliberate deviation from the tech spec's "facet" naming. The delete key is a composite `doc_key = "<account_id>\u{1f}<event_id>"` so a per-account delete removes exactly one document (the same `event_id` can exist under two accounts). The schema is versioned so this can be revisited with a clean rebuild.
- **The query path (used by 9b) hydrates from Postgres.** Tantivy ranks (BM25 default) and returns `(account_id, event_id)`; the API hydrates each via `get_event`, so Postgres stays the source of truth and a since-redacted hit is dropped on hydrate. Cross-account by default, `account_id` an optional filter; offset/limit pagination (BM25 score doesn't compose with the timeline cursor). Search disabled → ingestion hooks are no-ops and `GET /v1/search` returns `503` (9b).
- **Dependency direction.** `axon-search` is a leaf (`axon-core` + `axon-store` only); `axon-sync` → `axon-search` directly (the producer *is* `axon-sync`, no port inversion, no cycle), and 9b's `axon-api` → `axon-search` is likewise direct (matrix-free, like `axon-store`).

Non-obvious choices made in 8a (relation aggregation backend — see ADR 0033):

- **Aggregation is computed at read time, not materialized.** Two partial expression indexes over `events.relates_to` (`20260620120000_relation_aggregation_indexes.sql`) make "all relations pointing at X" an index lookup; the resolution happens in SQL on read, not as tallies maintained on ingest. The raw edit/reaction events stay on disk untouched (append-mostly, same philosophy as read-time redaction masking, ADR 0015); the read folds them. Additive and backfill-free — applies retroactively to rows stored before M8 and automatically to the deep history M10 backfills in later.
- **Two indexes, because replies have no `rel_type`.** `events_relation_target_idx` keys `(account_id, rel_type, target event_id)` for edits/reactions/threads; `events_reply_target_idx` keys the nested `relates_to->'m.in_reply_to'->>'event_id'` for replies (which carry no `rel_type`, so the first index never sees them).
- **The shared `TIMELINE_SELECT` projection now does edit collapse + reaction tally.** It grew two `LEFT JOIN LATERAL`s (latest-valid-edit; per-emoji reaction tally) and an `accounts` join (for the reaction `me` flag) alongside the existing redaction-mask LATERAL. So `room_timeline`, `get_event`, `event_replies`, and `thread_timeline` all return the same resolved `TimelineRow` (now carrying `edited` / `edit_count` / `latest_edit_ts` / `reactions`) — one set of rules, one `FromRow`, and replies/thread members are themselves aggregated for free.
- **Resolution rules the homeserver doesn't enforce.** An `m.replace` is honored only when its `sender` equals the *original* event's sender (impersonation guard; ADR 0021 noted this is unenforced upstream), it is well-formed (`m.new_content` present), and its replacement `msgtype` matches the target's. The latest valid edit wins by `origin_ts DESC, id DESC` (deterministic on ties; `COUNT(*) OVER ()` carries the count alongside the `LIMIT 1` winner). A **redacted target wins over its edits** — the projection masks a redacted row even when a valid edit exists, so a redaction can't be undone by a later edit. Reactions dedup `(sender, key)` via `COUNT(DISTINCT sender)`; a redacted reaction drops from the tally. `event_replies` requires `rel_type IS NULL` so a thread member (which also nests an `m.in_reply_to` fallback) isn't double-counted as a plain reply. Thread `reply_count` includes redacted members (structure preserved so a redacted root doesn't make the thread vanish).
- **The room timeline collapses standalone relation events.** `room_timeline` excludes `m.replace` and `m.annotation` events (now surfaced on their target row); replies and thread members keep their own rows. `COALESCE(rel_type, '')` keeps NULL-`rel_type` rows (ordinary messages, replies) from being filtered out by the `NOT IN`. The forensic edit trail stays on disk for the 8b `…/edits` endpoint.

Non-obvious choices made in 8b (relation aggregation API surface — this PR):

- **8b is thin API plumbing over the 8a backend.** Handlers are pass-throughs over the `Store` reads (`event_reactions` / `event_replies` / `event_edits` / `room_threads` / `thread_timeline`); no aggregation logic lives in `axon-api`. New reads: `GET …/events/{event_id}/reactions` (per-emoji tally, keyed-by-emoji map — issue #22 Option A), `…/replies`, `…/edits` (forensic trail), `…/rooms/{room_id}/threads`, and `…/threads/{root_id}/timeline` (thread-scoped, reusing the room timeline's opaque cursor pagination verbatim). (8b review folded a few additive changes back into the 8a store SQL — see the unreact and bounded-reads bullets below.)
- **`EventDto` now carries the resolved view.** `from_row` maps the `TimelineRow` aggregation fields (`edited` / `edit_count` / `latest_edit_ts` / `reactions`) onto the wire, so the existing `room_timeline` / `get_event` endpoints serve the edited body in place with no stray edit rows — no new route needed (issue #22 Option B). On the `/v1/ws` live stream the `From<LiveEvent>` impl sets them to raw defaults (`edited:false`, `reactions:null`): a frame is a pre-aggregation event, and the read API is the authoritative resolved view (the live raw relation events still flow so clients can apply deltas — a dedicated aggregation-update WS frame is deferred, not MVP).
- **Empty, not 404.** All five reads return `200` with an empty collection when there's nothing (no reactions / replies / edits / threads, or an unknown event/root), matching `room_timeline`'s "an unknown room and an empty timeline are indistinguishable" stance — the store reads don't probe base-event existence, so adding a 404 would cost an extra query for no client benefit. The single-event `get_event` keeps its 404.
- **The reactions tally carries `my_event_ids` so clients can still unreact (8b review).** Collapsing the timeline strips the raw `m.reaction` rows, so a client can no longer scan events to find its own reaction ids to redact. The tally (both the `/reactions` endpoint and the on-row `reactions` map) therefore exposes `my_event_ids` — the account user's own reaction event ids for the key, the ids redacted to withdraw. `axon-tui` reads badges and unreact ids from this aggregated map (`collect_reactions` / `own_reactions_for`) rather than raw events. Regression: `unreact_uses_aggregated_reaction_ids_from_timeline` walks react → reload → unreact.
- **The TUI keeps that aggregate current with optimistic patches after react/unreact (8b review round 2).** Because the on-row `reactions` map is now the *sole* source of badges and unreact choices, and the collapsed timeline no longer carries the raw `m.reaction` row a mutation produces/redacts, `send_react` and `withdraw_reaction` patch the target message's tally in place (`apply_local_reaction` bumps `count`/`me` and records the returned id; `remove_local_reaction` drops the owner's ids, clears `me`, decrements the owner's single distinct-sender contribution, and removes an emptied key). Without this the badge would persist and `/unreact` would re-redact already-withdrawn ids until a manual reload. Tests: `local_react_makes_badge_and_unreact_available_before_reload`, `local_unreact_clears_badge_and_choice_before_reload`, `local_unreact_keeps_other_senders_count_and_drops_my_contribution`.
- **The non-paginated relation reads are hard-capped (8b review).** `event_edits` / `event_replies` / `room_threads` answer in one shot, so each `LIMIT`s at `RELATION_READ_CAP` (1000) to bound the row count against a pathological/hostile room. The paginated room/thread timelines remain the path for genuinely large result sets.
- **Reaction aggregation bounds a deduplicated, deterministically-truncated pair set (8b review rounds 2–3).** `RELATION_READ_CAP` caps grouped output rows, but each reaction tally also builds per-key `senders` / `my_event_ids` arrays and a variable number of keys — all unbounded if every matching `m.reaction` is aggregated, and the shared `TIMELINE_SELECT` had no key cap at all. Round 2 added a raw-scan `LIMIT`; round 3 fixed that it was *non-deterministic and evictable* (an unordered `LIMIT` before grouping, so one sender's duplicate reactions could consume the whole budget and hide other senders' reactions / the account's own `my_event_ids`). So both `event_reactions` and the `TIMELINE_SELECT` `react` LATERAL now **`DISTINCT ON (sender, key)`** first (keeping each pair's lowest `event_id`), then keep the **oldest `REACTION_AGG_PAIR_CAP` (1000) pairs by `(origin_ts, event_id)`** before grouping. Deduplicating before the cap means a single spammer can't evict others; the explicit order makes truncation stable across identical reads. Bounding the deduped pair set bounds `count`, both arrays, and the key cardinality on every timeline/get-event/reply/thread row. `my_event_ids` thus holds the account's canonical reaction id per key (a pathological double-react self-heals on the next read). `TIMELINE_SELECT` became a `LazyLock<String>` so the cap interpolates from the one constant.
- **The on-row `reactions` field is a typed map, not an opaque object (8b review).** `EventDto.reactions` is `Option<BTreeMap<String, ReactionDto>>`, so the OpenAPI references `ReactionDto` for the map values (generated clients can type `count` / `me` / `senders` / `my_event_ids`). `from_row` deserializes the store's reactions JSON into the typed map; a malformed/absent tally degrades to `None`.

Non-obvious choices made in 7b (bearer-token auth — see ADR 0029):

- **One bearer-token gate over all of `/v1/`, replacing the loopback guards.** Every `/v1/` route — HTTP and the WebSocket, including the lifecycle verbs — now requires a valid `Authorization: Bearer <token>`; the per-route `require_loopback` guards and the `loopback` module are gone, and the lifecycle verbs are reachable off-box *with* a token. The HTTP gate is a single `require_bearer` layer (`from_fn_with_state`) over a `/v1` sub-router, so no route can be added without it; `/healthz` sits outside the gate. The WebSocket can't ride that layer (a browser can't set a header on a socket), so `ws_handler` checks the token itself at upgrade time — from the `Authorization` header **or** a `bearer.<token>` `Sec-WebSocket-Protocol` entry — and rejects with `401` before upgrading.
- **Tokens are global, hashed, and behind a `TokenVerifier` port.** The `tokens` table is `(id, label, hash, created_at, last_used_at, revoked_at)` — no `account_id` (one human owns all accounts; per-account authz is a non-goal). A token is high-entropy, so it's stored as a plain **SHA-256** (base64), not encrypted (cf. the access token's `pgp_sym_encrypt`, ADR 0008) and not a slow password KDF; `verify_token` is one `UPDATE … WHERE hash = $1 AND revoked_at IS NULL RETURNING id` that matches and stamps `last_used_at` in a single round-trip. Revocation tombstones (`revoked_at`), never deletes. Verification sits behind `axon-api`'s `TokenVerifier` trait (`AppState` holds `Arc<dyn TokenVerifier>`; shipped impl `StoreTokenVerifier`), the seam a future OAuth issuer replaces without changing the `Authorization` wire contract or any route.
- **CLI bootstrap via a clap subcommand layer.** `axon` with no subcommand runs the server as before; `axon token issue --label <name>` / `list` / `revoke <id>` connect only the store (no sync engine, no HTTP) — `issue` prints the raw token once to stdout (logs go to stderr), `list` never prints a secret. The OpenAPI doc now declares an HTTP-bearer security scheme with a global `security` requirement. `axon-tui` does not yet send the token (separate client work).

Non-obvious choices made in 6 (see ADR 0021):

- **Consumer-owned port + composition-root adapter.** `axon-api` defines the `MessageSender` trait it needs (`send_message`/`edit`/`redact`/`react`; `AppState` holds `Arc<dyn MessageSender>`) and stays free of `axon-sync`/`matrix-sdk`. `axon-sync` exposes a concrete `SdkGateway` implementing **no foreign trait**; `axon-server` owns the `GatewayAdapter` newtype that `impl MessageSender` and maps `axon_sync::GatewayError → axon_api::SendError`. `axon-core` stays pure data. `axon-api` and `axon-sync` never depend on each other.
- **`ClientManager` (connection) vs `SdkGateway` (message semantics).** The manager is the single owner of per-account `Client`s — build/auth/cache via `get_or_connect`, `evict`, with a per-account single-flight guard. The gateway only builds ruma content and sends. Both share the *same* client per account (same crypto store + send queue).
- **Lazy connect; supervisor still owns retry.** The supervised sync loop remains the always-on driver (`get_or_connect` → run sync → on failure `evict` + backoff). The gateway connects lazily through the same `get_or_connect`. A send during a homeserver outage returns `503`/`502` and is retried by the client — correct, since unreachability is a normal recurring condition the supervisor rides out.
- **Wire shape.** Routes nest `account_id` in the path (M5a convention); every mutation returns `{ "data": { "event_id": "$…" } }` at `200`. The created event is not echoed — it round-trips through sync into the timeline read and `/v1/ws`. Edits are sent as a raw `m.replace` envelope. Redact reason is `?reason=`. The SDK mints a fresh txn id per send, so a client retry can duplicate (acceptable pre-auth; revisit M8).

Non-obvious choices made in 5b (see ADR 0020):

- **Live-event bus = `tokio::sync::broadcast`, owned by the sync engine.** `SyncEngine::live_events()` hands a `broadcast::Sender<LiveEvent>` clone to `AppState`; the `/v1/ws` handler `subscribe()`s once per connection. A slow client gets `RecvError::Lagged` (skips the backlog, stays connected) — sync is **never** back-pressured by a client. Capacity 1024; the producer skips the work entirely when `receiver_count() == 0`.
- **`LiveEvent` lives in `axon-core`** (the only crate both sibling producers/consumers share) and is **wire-neutral**; `axon-api` owns the envelope and maps `LiveEvent → EventDto`. The WS payload is the **same `EventDto`** the read API returns.
- **Wire envelope** `{ "type": "timeline.event", "account_id": <uuid>, "payload": <EventDto> }`. `type` is namespaced so M5c verification frames extend it without colliding. Live frames are always `redacted: false` (a redaction is a separate later event).
- **Live tail, not replay.** `/v1/ws` delivers events arriving *after* connect; history is the HTTP read API's job. Not in the OpenAPI doc (a WS upgrade isn't expressible in OpenAPI 3.1) — golden test unaffected. No auth yet (M8). Re-decryption back-fill of a UTD is **not** re-emitted over WS (documented scope limit).

Non-obvious choices made in 5a (see ADR 0019):

- **Account-nested canonical routes.** `GET /v1/rooms` is the flat cross-account aggregate (newest-activity first, optional `?account_id=` filter); detail routes nest the account: `GET /v1/accounts/{account_id}/rooms/{room_id}/timeline` and `GET /v1/accounts/{account_id}/events/{event_id}` (event under the **account, not the room** — the store keys events by `(account_id, event_id)`). A deliberate deviation from the spec's literal flat routes, consistent with M7's already-nested `/v1/media/{account_id}/…`. **Convention going forward: nest `account_id` on all account-scoped resource routes** — so M6 mutations become `/v1/accounts/{account_id}/rooms/{room_id}/send`, dropping `account_id` from the body.
- **Response envelope.** Success is `{ "data": <T> }` (`ApiResponse<T>`), errors `{ "error": { "code", "message" } }` (`ApiError`), each with one `IntoResponse`. `StoreError` → logged `500` with a generic body. Missing event → `404`; bad cursor/param → `400`; an unknown room's timeline is an empty `200` page, not `404`.
- **Opaque cursor.** The store's `(origin_ts, id)` `TimelineCursor` is serialized to the wire as base64url(`"{ts}.{id}"`), returned as `next_cursor` per page (`null` at the end); a malformed cursor is a `400`. Codec in `crates/axon-api/src/cursor.rs`.
- **`AppState` + `FromRef` seam.** `axon-api::router` takes `AppState { store }` and handlers extract `State<Store>` via `FromRef`, so 5b can add a `broadcast::Sender` field with zero churn to existing handlers.
- **OpenAPI golden file.** utoipa builds the spec from handler signatures; a DB-free test diffs it against `openapi/openapi.json` (regenerate with `UPDATE_OPENAPI=1 cargo test -p axon-api --test openapi`), making drift a CI failure. TypeScript client stubs are deferred to M11.
- **Store reads (no new tables/migration).** `list_rooms(Option<account_id>)` aggregates `events` for activity + latest event id and pulls name/topic/avatar/alias from the `room_state` projection in one query (note avatar state is `m.room.avatar` → `content.url`). `get_event(account_id, event_id)` reuses `room_timeline`'s read-time redaction masking via a shared `TIMELINE_SELECT` projection.

Non-obvious choices made in 4a (see ADR 0015):

- **Hot columns + indexes (`events`):** `redacts`, `relates_to` (JSONB, captured generically incl. `m.thread` but not thread-indexed — threads deferred), `decrypted_body_text`; plus `(account_id, room_id)` and a partial `(account_id, redacts) WHERE redacts IS NOT NULL` index. Unique stays `(account_id, event_id)` (account-scoped), a deliberate deviation from the spec's literal `(event_id)`.
- **Crypto sibling tables** keyed 1:1 by `(account_id, event_id)`, FK→`events` ON DELETE CASCADE: `event_ciphertext`, `event_megolm_session`, `event_sender_device_keys`. The megolm + device siblings come from the SDK's `EncryptionInfo` (handler extractor `Option<EncryptionInfo>` on the live path; `Arc<EncryptionInfo>` on the re-decryption path) for **every decrypted event**. **`event_ciphertext` is written on the UTD path only** — the SDK never surfaces the ciphertext of events it decrypts before dispatch, so live-decrypted events have no ciphertext row (documented limitation, ADR 0015). Sibling writes are best-effort: logged, never fatal to sync. The pure extractors live in `crates/axon-sync/src/meta.rs`.
- **`Store::room_timeline`:** newest-first, cursor on `(origin_ts, id)` (the `BIGSERIAL` `id` is the tiebreaker so pages never overlap/skip). Redaction is masked **at read time** via a `LEFT JOIN LATERAL` (LIMIT 1) — `content`/`decrypted_body_text` nulled, `redaction_event_id` set — leaving the stored row and ciphertext sibling untouched. No HTTP endpoint yet (that's M5); verified via `--ignored` store tests.
- **Sliding-sync timeline depth:** the SDK default is **1** (latest event only — the root of M3's latest-only archive). Raised via `SyncServiceBuilder::with_room_list_timeline_limit`, driven by new `sync.timeline_limit` (default 20). Deepens new syncs only; not retroactive backfill.
- **M4 re-scope (ADR 0011, 0015):** the recovery-key bootstrap landed in M3c (transient-only, kept that way — the M4 at-rest review is closed in ADR 0015); the interactive **verification plumbing moved wholly to M5** (untestable before `/v1/ws`), so `axon-crypto` stays a stub until M5.

Non-obvious choices made in 4b (see ADR 0016):

- **`room_state` / `account_data` are current-value projections**, upserted in place — not logs. The raw events still land in `events` (state events are part of the timeline); these tables hold the resolved latest value a room-summary or read-marker read needs. `room_state` PK is the Matrix state identity `(account_id, room_id, event_type, state_key)`; `account_data` PK is `(account_id, room_id, event_type)`.
- **Global account data uses `room_id = ''`** (a `NOT NULL DEFAULT ''` sentinel — real room ids start with `!`), so the natural PK carries uniqueness and `ON CONFLICT` targets it directly. A nullable `room_id` would make two global rows for one type "distinct" under SQL NULL semantics and defeat the upsert. The store API maps `room_id: Option<&str>` ↔ `''` at the boundary.
- **`room_state` upsert is freshness-guarded** (`ON CONFLICT … DO UPDATE … WHERE EXCLUDED.origin_ts >= room_state.origin_ts`): an older replayed state event can't clobber newer state. `account_data` events carry no timestamp, so theirs is plain last-write-wins.
- **Three new SDK handlers** (`crates/axon-sync/src/engine.rs`): `persist_state_event` (`AnySyncStateEvent`), `persist_room_account_data` (`AnyRoomAccountDataEvent`), `persist_global_account_data` (`AnyGlobalAccountDataEvent`). All reuse the one `PersistContext`. The global handler takes **no `Room` argument** — global account data has no room, and the SDK skips a handler whose `Room` extractor fails. `updated_at` on both tables is maintained by the shared `trigger_set_updated_at()` trigger.

Non-obvious choices made in 3c (see ADR 0014):

- **Re-decryption queue (`crates/axon-sync/src/redecrypt.rs`):** two drivers — the SDK's `room_keys_received_stream()` (drains the pending UTDs for each arriving `(room_id, session_id)`) and a startup sweep (catches keys already in the crypto store or imported by `recover()` before we subscribe). By default the startup sweep is a bounded, one-time-per-row pass: `SweepScope::StartupUnattempted` selects only rows that have never had a startup attempt (`utd_startup_redecrypt_attempted_at IS NULL`) and marks each attempted row afterward so it is not retried on every boot (issue #9). Operators can opt into the legacy every-boot full sweep (`SweepScope::AllPending`, `always_redecrypt_utds_on_startup=true`), and the same `AllPending` scope backs the explicit `POST /v1/accounts/{id}/utds/redecrypt` retry endpoint. The sweep first calls `backups().download_room_keys_for_room()` per room — `recover()` imports the backup *decryption key* but not the megolm room keys themselves, so on a quiet account nothing else would fetch them; the arrival-stream path skips the download (its keys just landed). Runs as a child task of `run_account` on a child `CancellationToken`, joined on return. Per-row failures are logged and skipped — never fatal to sync. ADR 0014.
- **`events.megolm_session_id` hot column + partial index:** UTDs lift `content.session_id` into a first-class column; `events_pending_utd_idx (account_id, room_id, megolm_session_id) WHERE content IS NULL` makes the arriving-key lookup an index hit rather than a JSONB scan. The back-fill `UPDATE … WHERE content IS NULL` guard is idempotent and won't clobber a row a live dispatch already decrypted.
- **Transient `recover()` (ADR 0011, 0014):** originally consumed a config-supplied `sync.account.recovery_key` once on boot to import the megolm backup + cross-signing keys (the queue's driver on a fresh, unverified device); that boot path is retired along with the rest of config-based provisioning (ADR 0024) — the recovery key is now always supplied via `POST /v1/accounts/{id}/recover` (7a-5, ADR 0026) instead. Never persisted either way — no column on `accounts`; durable at-rest storage + interactive verification stay in M4/M5.

Non-obvious choices made in 3b (see ADR 0012):

- **Event persistence hook:** `Client::add_event_handler(persist_timeline_event)` with `AnySyncTimelineEvent` + `RawEvent` context. Registered on the `Client` before `SyncService::start()` so no events are missed during initial sync. matrix-rust-sdk decrypts Megolm payloads before dispatch, so `raw_event` in the `events` table holds the plaintext envelope for decrypted events (or the `m.room.encrypted` envelope — ciphertext + `session_id` — for UTDs). ADR 0012.
- **Timeline coverage is latest-event-only (current limitation):** the handler persists the events Simplified Sliding Sync surfaces, which is the *latest* timeline event per room — not full room history. Seeding a room with N messages and syncing a fresh device archives ~1 event (the most recent), so the integration test asserts on the count axon actually archived, not on how many were sent. Per-room timeline backfill is future work (M4+).
- **Events table:** `(id BIGSERIAL, event_id TEXT, room_id TEXT, account_id UUID, sender TEXT, origin_ts BIGINT, event_type TEXT, content JSONB, raw_event JSONB, provenance TEXT DEFAULT 'upstream_homeserver', received_at TIMESTAMPTZ)`. `raw_event` is the full event envelope as dispatched (plaintext for decrypted events, the `m.room.encrypted` ciphertext for UTDs); `content` is the extracted decrypted payload. Unique on `(account_id, event_id)` — upsert is idempotent. `content` is nullable: UTDs arrive as `m.room.encrypted` with `content = NULL`; the M3c re-decryption queue back-fills those rows, reading the ciphertext straight from `raw_event`. Index on `(account_id, room_id, origin_ts DESC)` for timeline reads. M4 ("Event store schema") adds hot-column refinements and sibling tables holding the original ciphertext + megolm session metadata + sender device keys (keyed by `event_id`, for every event) so decrypted rows stay re-verifiable against Matrix's signatures — distinct from M3c re-decryption, which reads UTD ciphertext straight from `raw_event`.
- **sqlx JSONB:** added `json` feature to `sqlx-postgres` (transitively enables `sqlx-core/json`) so `serde_json::Value` binds as JSONB.
- **Ctrl-C shutdown investigation (ADR 0013):** a post-3b hang turned out to be caused by an inherited blocked signal mask in the developer's terminal session (`SIGINT` blocked in the kernel pending queue, never delivered to any handler). No code change to axon was needed. The original `with_graceful_shutdown` + `tokio::signal::ctrl_c()` shutdown path is correct. If Ctrl-C does not work, run `python3 -c "import signal; print(signal.pthread_sigmask(signal.SIG_BLOCK, []))"` — if `2` appears, open a new terminal window.

Non-obvious choices made in 3a (see ADRs 0006–0008, 0010, 0011):

- **Dependency conflict:** adding `matrix-sdk` (→ rusqlite → `libsqlite3-sys 0.35`) collides with the `sqlx` umbrella's `sqlx-sqlite` (`libsqlite3-sys` 0.28–0.30) over the `links = "sqlite3"` native lib. Fix: drop the umbrella for `sqlx-core` + `sqlx-postgres` directly (pinned `=0.8.2`), embed migrations via `include_dir` (hand-built `Migrator`, same checksum format as `sqlx::migrate!`), and align sqlx onto the **aws-lc-rs** rustls provider to match matrix-sdk (two providers → runtime TLS panic). ADR 0006.
- **Sync:** `matrix_sdk_ui::sync_service::SyncService` (not the low-level `SlidingSync`); one `Client` + one SQLite store per account under `sync.data_dir/<account_id>`; one supervised task per account, restarted with exponential backoff on `SyncService` `Error`/`Terminated`; `CancellationToken` for graceful drain. ADR 0007.
- **Auth:** login once, restore thereafter. Access token stored encrypted at rest via pgcrypto `pgp_sym_encrypt` keyed by `sync.store_key`; password consumed once, never stored. Tokens treated as long-lived; `M_UNKNOWN_TOKEN` recovery + MSC2918 refresh deferred to M4. ADRs 0008, 0010.
- **sqlx queries:** runtime `query`/`query_as` (no `query!` macros, no compile-time DB); `FromRow` hand-implemented. CI stays DB-free; account store methods covered by `#[ignore]` integration tests (`cargo test -p axon-store -- --ignored` with `DATABASE_URL`).
- **E2EE key acquisition (deferred at 3a; see ADR 0011 Status):** a fresh `axon` device is unverified, so encrypted rooms show UTDs until it obtains keys. Two complementary paths (ADR 0011): the *bootstrap/fallback* account **recovery key** (Secure Storage / 4S) — one `recover()` call unlocks both key backup and cross-signing — **landed in M3c** (transient-only); the *mature* path, **BFF-proxied interactive verification** (axon streams the SAS emoji over `/v1/ws` so the user verifies the axon session from the axon client; after trust, the user's other devices gossip the secrets so the recovery key never touches the server), is **M5**.

Non-obvious choices made in Milestone 2 (see ADRs 0002–0003):

- **Config:** figment (TOML + env). Precedence low→high: defaults < TOML file < `DATABASE_URL` < `AXON_`-prefixed env (`__` = nesting, e.g. `AXON_SERVER__PORT`). File resolved from an explicit `--config`/`Config::load_from` path, else `$AXON_CONFIG`, else `./axon.toml`, else `<platform config dir>/axon.toml`, else env-only. Sample at `axon.toml.example`.
- **Defaults:** bind `127.0.0.1:8080`; pool `max_connections = 5`; log `info` (overridable by `RUST_LOG`).
- **Store:** sqlx with `tls-rustls` (no OpenSSL); migrations embedded via `sqlx::migrate!`. `Store` is a `Clone` handle over `PgPool`, shared into `axon-api` as router state.
- **Migrations:** baseline migration only enables `pgcrypto` (no tables until M3–4). Timestamp-prefixed filenames — see ADR 0004.
- **`/healthz`:** liveness-only, always 200, no DB ping.
- **Errors:** top-level `axon_core::Error` is acyclic — its `Store(String)` variant carries a message so `axon-core` need not depend on `axon-store`; leaf crates impl `From<LeafError> for axon_core::Error`.
- **CI:** unchanged. No `query!` macros yet, so sqlx compile-time checks aren't triggered and tests need no DB. When checked queries land in M3, add a Postgres service or a `.sqlx` offline cache.
- **Pre-commit hook:** `.githooks/pre-commit` runs the fmt + clippy subset of CI; enable per clone with `./scripts/setup-hooks.sh` (`core.hooksPath`). Full `cargo test` stays in CI.
