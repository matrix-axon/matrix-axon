# ADR 0107 — Android builds are signed with an upload key, after the build

**Status:** Accepted.
Implemented in `scripts/package-android.sh` alongside this record.

## Context

ADR 0102 ships the same Tauri shell to Android through Google Play (M-W13), with the internal track as the exit criterion.
Play takes an Android App Bundle (`.aab`), not an APK, and a bundle has to be signed before it is uploaded.
Nothing signed Android builds yet: `tauri android build` produces `app-universal-release.aab` and `app-universal-release-unsigned.apk`, and a release APK without a signature will not install at all.

Two facts shape the answer.

**Play re-signs.** With Play App Signing, which is the default for new apps and mandatory for bundles, Google holds the key that signs what users install.
The key we hold is an *upload key*: it only tells Google an upload came from us.
If it is lost or leaks, Google support can register a new one; the app's identity on devices is unaffected.
That is a much cheaper failure than losing a key that signs a direct-download APK, where users on the old key can never upgrade to a build on a new one.

**The generated project is not ours to edit.**
`gen/android` is regenerated by `tauri android init` and gitignored, as `gen/apple` is (ADR 0102).
Its `build.gradle.kts` is the natural place for a `signingConfigs` block and is the one place that block would not survive.

## Decision

### An upload key, generated locally, kept outside the repo

RSA 4096 in a PKCS12 keystore, valid 25 years, made with `keytool -genkeypair -storetype PKCS12 -keyalg RSA -keysize 4096 -validity 9125`.
The keystore never enters the repository, and `.gitignore` refuses `*.jks`, `*.keystore`, `*.p12` and `keystore.properties` so one dropped into the tree by accident cannot be committed.
It is backed up in a place separate from the machine that builds: a lost upload key is recoverable through Play support, but that is a support ticket and days, not a command.
PKCS12 means the key password and the store password are one, so there is a single secret to supply.

### Signing happens after the build, not inside Gradle

`scripts/package-android.sh --sign` builds unsigned and signs the result: `jarsigner` for an `.aab`, and `zipalign` then `apksigner` for an `.apk`.
Alignment comes first because `apksigner`'s whole-file signature would be broken by aligning afterwards.
This leaves Gradle's configuration exactly as generated, so nothing is lost when the project is regenerated, which the script does on every run.
The signature is checked before the script reports success (`jarsigner -verify` exits non-zero on an unsigned bundle, measured), and the certificate's SHA-256 is printed: it is what Play Console asks for when the key is registered, and what to compare if an upload is refused for a signature mismatch.

### Secrets arrive through the environment

`ANDROID_KEYSTORE`, `ANDROID_KEY_ALIAS` and `ANDROID_KEYSTORE_PASSWORD`, all checked before the build starts so a forgotten one does not cost a release build.
The password is passed to the signing tools as `-storepass:env` and `--ks-pass env:`, never as an argument, because an argument is readable in `ps` and lands in shell history.

### `versionCode` is derived, with an override, or asked of Play

Tauri derives `versionCode` from the version (`major*1000000 + minor*1000 + patch`, so 0.1.3 is 1003), which release-plz (ADR 0106) already makes monotonic.
Play refuses a reused `versionCode`, so uploading the same version twice needs `--version-code`, carried as a `bundle.android.versionCode` config override for the same reason iOS's build number is: the project it would otherwise be written into is regenerated.

`--version-code auto` does what `--build-number auto` does for the Apple builds: it asks the store for the highest number it has and adds one, so the caller does not have to remember.
`scripts/lib/play-next-version-code.py` signs a short-lived token with a Google Cloud service-account key (Python's standard library and `openssl`, nothing installed), opens a read-only Play "edit", takes the highest `versionCode` among the app's bundles and its release tracks, deletes the edit, and prints that plus one.
It is resolved before anything is regenerated or compiled, so a bad credential costs seconds, and it needs `--aab`, since only a bundle going to Play has any use for it.

It needs a service account that is invited in Play Console with permission to view the app and its releases, with the Google Play Android Developer API enabled in the key's Cloud project, and the key's path in `PLAY_SERVICE_ACCOUNT_JSON`.
The key stays out of the repository, like the upload keystore, and is read only to sign that token.
Play's API works only on an app that has had its first upload through the Console, so `auto` cannot number the very first bundle.

What it cannot see: a `versionCode` used by a bundle that was uploaded and later discarded, which Play still refuses, and a bundle that is still being processed.
In either case the upload fails with Play's own message and the next try needs a higher number, which `--version-code` takes explicitly.

### Uploading to Play from the script

`--upload check|draft|release` sends the signed bundle and its native debug symbols to the internal track, through `scripts/lib/play-upload.py` and the same service account.
Everything happens inside one Play "edit", which is how the API is shaped: nothing is visible until it is committed.

`check` uploads, lets Play inspect the bundle, validates the edit and then discards it.
Nothing is published and the `versionCode` stays free, so it is the mode for a first run of the pipeline, and a cheap way to learn that Play would accept a bundle.
`draft` commits the bundle as a draft release, keeping the track's existing releases, and refuses if the track already has a draft rather than replace someone's work; testers see nothing until it is completed in Play Console.
`release` commits a completed release, which replaces what the track had, because that is what completing one means.
It needs `--aab --sign`, and uses the symbols zip from the same build, since Play matches symbols to a bundle by build ID.

The service account needs permission to release to testing tracks, beyond the read access `--version-code auto` needs.
Only the internal track is wired to the script; the helper itself takes any track.

## Consequences

- A signed bundle is one command: `scripts/package-android.sh --aab --sign` with the three variables set.
- A locally signed release APK installs on a device or emulator, which is how the release configuration (non-debuggable, `usesCleartextTraffic` false) gets tested without Play. It has to replace a debug build with `adb uninstall` first: the signatures differ, and Android refuses the update.
- **A sideloaded APK and the Play build carry different signatures.** Play signs with Google's key, this script with ours, so a user cannot upgrade one to the other. If a GitHub-release APK is ever offered next to the store build, it needs its own decision about which key signs it, made before the first one ships. That decision, and Google's developer verification for apps installed outside Play, are not made here.
- **Not automated.** No CI lane builds or signs Android; one would need the keystore as an encrypted secret and is a separate change.
- **Verified with a throwaway key, not the real one.** The real upload key does not exist yet and is generated by the person who owns the Play account.
- **Measured** on the API 35 emulator (Pixel 8 image) with a throwaway key: a signed `.aab` verifies and reports the expected certificate; the same build unsigned does not; a release APK signed this way installs and `apksigner verify` reports the same certificate; `--version-code 1004` produces `versionCode=1004` in the generated properties.
