# ADR 0116 — The web client ships inside the server binary

**Status:** Accepted.
Step 1 (the server serves an embedded bundle) is implemented with this record.
Steps 2 to 4 are the sequence below.

## Context

The web client reaches users one way today: the Docker stack.
`deploy/web/Dockerfile` builds `clients/web` and copies `dist/` into a `caddy:2` image, and that container serves the bundle and reverse-proxies `/v1/*`, `/healthz` and `/bootstrap/*` to `axon-server` (ADR 0052 § 5).

Someone who installs the `.deb`, the `.rpm` or the Homebrew formula gets no web client.
The server answers `/` with a page that says "No web interface is served at this address", and `packaging/README.md` says "Docker Compose remains the path that includes Postgres and the web client".

Three facts shape what packaging the web client can mean:

- **The web client is not installed by the person who uses it.**
  It is a static bundle that a browser downloads.
  The question is never "how does a user install the web client", it is "does the operator's server package serve it".
- **The bundle and the API must share an origin.**
  The server sends no CORS headers: ADR 0046 designed them, ADR 0052 chose a same-origin front door instead, and ADR 0102 gave the native shells a Rust-side transport so that they would not need them either.
  The client's API base defaults to `/`.
  A bundle served from anywhere else cannot call the API without a reverse proxy in between.
- **The server already owns every non-API path.**
  The router has a fallback for them, and it is the page quoted above.

So a separately packaged web client is not a smaller thing than a web client in the server.
It is the same bundle plus a reverse proxy the operator must install and configure before the first page loads.

## Decision

The built web client is compiled into `axon-server` and served by it, from the listener the API already uses.
This supersedes the line in ADR 0052 § 5 that the server serves no static assets.

### Embedding

`axon-api` gains a cargo feature, `embed-web`, that `axon-server` forwards.
With it, `crates/axon-api/build.rs` reads `clients/web/dist` (or the directory named by `AXON_WEB_DIST`) and generates a table of `include_bytes!` entries.
The feature is off by default.
A plain `cargo build` and `cargo test` need neither Node nor a built bundle, and behave as they do today.

What a missing bundle means depends on who named the directory.

- `AXON_WEB_DIST` is an explicit path, and the project treats explicit paths as promises.
  A directory there with no `index.html` fails the build.
  The release pipelines set it (step 2), because a release artifact that silently lacks the web client would be worse than a failed build.
- The default location may simply not have been built.
  That is a cargo warning and an empty table.
  It cannot be an error: the pre-push gate and CI run `cargo clippy --all-features` on checkouts that never ran `pnpm`, and the first draft of this change failed that gate for exactly this reason.

Either way the server's startup log says whether the binary carries the web client.

The table is generated by a build script instead of `include_dir`, which the workspace already uses for migrations, because the bundle is built by another tool at another time.
The script tells Cargo to watch the directory, so a rebuilt bundle rebuilds the crate.
`include_dir` cannot do that on a stable toolchain, and a stale bundle in a release binary is the failure this record most needs to rule out.
No dependency is added.

The bundle is 3.4 MB uncompressed at the time of writing, and it is stored uncompressed.

### Serving

The router's fallback answers from the bundle.
The rules are the ones `deploy/web/Caddyfile` established, for the reasons in ADR 0087:

| Path          | Hit                                                            | Miss                                    |
| ------------- | -------------------------------------------------------------- | --------------------------------------- |
| `/assets/*`   | the file, `Cache-Control: public, max-age=31536000, immutable` | `404`, `Cache-Control: no-store`        |
| anything else | the file, `Cache-Control: no-cache`                            | `index.html`, `Cache-Control: no-cache` |

A missing `/assets/*` file must not fall back to `index.html`.
It is a chunk that a newer build no longer has, requested by a tab still running the old one, and HTML with a `200` hangs that tab.

Every response carries a strong `ETag` derived from the content, and a matching `If-None-Match` gets a `304`.
The validator is a hash of the bytes, so it is stable across restarts.
Responses also carry `X-Content-Type-Options: nosniff`, which the Caddy front door does not send.
Only `GET` and `HEAD` are answered; anything else is `405`.

Lookups are exact matches against the table's keys.
Nothing is read from disk at request time, so there is no path to traverse.

`/v1/*`, `/healthz` and `/bootstrap/*` are routes and are matched before the fallback, so they behave exactly as before.
The existing compression layer negotiates gzip, brotli or zstd for the bundle as it does for JSON.

### The switch, and where the web client is reachable

`[server] web_client` (`AXON_SERVER__WEB_CLIENT`) defaults to `true`.
Set it to `false` and the server answers non-API paths with the "no web interface" page, as a build without the feature does.

The web client has no listener of its own, and it cannot have one: a second port is a second origin.
It is reachable exactly where the API is.
The default `host` is `127.0.0.1`, and a non-loopback bind is refused unless `allow_insecure_bind` is set, so a default install serves the web client to the local machine only.
That is the answer to "expose it on localhost by default": it already is, and no new setting is needed to keep it there.

Turning the web client off does not reduce what a remote attacker can reach, since the API is on the same socket.
The switch exists for an operator who does not want the server to offer a UI, not as a security boundary.

### First sign-in

When the process serves the web client and `server.web_client_url` is unset, the first-credential bootstrap treats the web client's address as `/`.
The bootstrap success page is then same-origin with the client, writes the new token into its `localStorage`, and redirects (the ADR 0052 handoff).
An explicit `web_client_url` still wins.

The `.deb` and `.rpm` already arm the bootstrap and print its URL at install.
With the web client embedded, opening that URL ends in a signed-in web client with nothing to copy.

### No prompt at install

The packages do not ask whether to enable the web client.

- The safe answer is already the default: loopback only, behind a bearer token.
- Only Debian has a mechanism for it (debconf).
  RPM scriptlets must not read from the terminal, and Homebrew has no install-time prompts.
  One format would behave differently from the other two.
- A prompt blocks or is silently defaulted under `DEBIAN_FRONTEND=noninteractive`, Ansible, image builds and CI, which is how a server package is most often installed.
- The choice is one line in the config file and one restart, and it is as easy to make a week later as at install.

Without a prompt, the text the operator reads is the only place the choice is offered, so it is a requirement of step 3 and not a courtesy.
The install output, and the documentation each format installs, must each state all of the following in plain words:

- that the web client is on, and the address to open;
- that it is reachable from this machine only, and why (`server.host`);
- the one line that turns it off (`web_client = false` under `[server]`, and the restart that applies it), with the path of the config file on that platform;
- how to reach it from another device, pointing at the reverse-proxy and Tailscale instructions below, and that this should wait until the first sign-in is done.

Where that text lives:

| Format         | At install                                        | Installed documentation                                                 |
| -------------- | ------------------------------------------------- | ----------------------------------------------------------------------- |
| `.deb`, `.rpm` | the postinstall output, next to the bootstrap URL | `/usr/share/doc/axon-server/README.Debian` and the man page             |
| Homebrew       | the formula's caveats                             | the formula's `doc` directory, `$(brew --prefix)/share/doc/axon-server` |

The Homebrew caveats are also shown again by `brew info axon-server`, which is where an operator looks later.

### Reverse proxies: detect and advise, never edit

Remote access needs TLS, and the server terminates none.
The packages help with that and stop short of doing it.

- The packages ship ready-to-use site files for Caddy, nginx and Apache under the package's documentation directory, each a complete same-origin proxy for this server including the `/v1/ws` upgrade and no request-body cap.
- At install, the package detects which of those servers is present and prints the two or three commands that enable the matching file, and the `tailscale serve` line the Homebrew caveats already carry.
- The package never writes into another server's configuration directory and never reloads another service.

The reasons it stops there:

- **It cannot know the hostname.**
  A site file needs a server name and a certificate.
  Any value the package guessed would be wrong, and a proxy enabled on the default virtual host would publish the server on whatever that host already serves.
- **It would turn a loopback-only install into a network-facing one as a side effect of `apt install`.**
  That is the opposite of the default this record keeps.
- **A same-host proxy defeats the bootstrap's loopback check.**
  The first-credential bootstrap is restricted to loopback peers.
  Behind a proxy on the same machine every request arrives from `127.0.0.1`, so the restriction no longer distinguishes the operator from anyone who can reach the proxy.
  The six-character code and the six-wrong-URL lockout still apply, but the operator should enable a proxy after the first credential exists, and the shipped instructions say so.
  An install script that wired up the proxy before the first sign-in would create exactly that window.
- **Editing another package's configuration is not ours to do.**
  Debian policy forbids a package from modifying another package's conffiles, and a failed `nginx -t` after our edit takes down sites that have nothing to do with Axon.

A later `axon-server` subcommand that prints a site file for a named proxy and hostname would remove the copy-and-edit step without crossing any of these lines.
It is not part of this record.

## Sequence

The work is split by layer, not by package format.
The `.deb`, the `.rpm` and the Homebrew formula all repackage one binary, so once that binary carries the web client all three have it.
A pull request per format would be three copies of one change.
The one-silo rule separates the layers anyway.

1. **Server (this record).**
   The `embed-web` feature, the fallback, the `web_client` switch, and the bootstrap default.
   No released artifact changes, because nothing turns the feature on yet.
2. **Build.**
   `package.yml`, `cross-build.yml` and the root `Dockerfile` build `clients/web` and pass `--features embed-web`.
   A CI job builds and tests with the feature, so it cannot rot between releases.
   This is the change that puts the web client in the `.deb`, the `.rpm` and the Homebrew formula.
3. **Packaging.**
   Install output, `README.Debian`, the man page, the Homebrew caveats (which today say Tailscale "exposes the API, not the web client"), `packaging/README.md`, and the proxy site files and detection above.
4. **Docker, optional.**
   The `web` Caddy container becomes redundant once the server image serves the bundle.
   Removing it changes the stack's topology and is worth its own decision.
   Until then the stack keeps working unchanged, because Caddy answers non-API paths before the server sees them.

## Consequences

- The server's release builds need Node and pnpm.
  Local development does not.
- The web client and the server are versioned together in native packages.
  A web-only fix reaches those users with the next server release.
  ADR 0087's `version.json` and refresh prompt work unchanged, since a new binary is a new bundle and the restart drops every WebSocket.
- A bundle built from a checkout with uncommitted changes stamps `version.json` with a dirty marker.
  Release pipelines build from a clean tag, and step 2 must keep it that way.
- The binary grows by the size of the bundle.
- AppImage is not a target for this.
  The server is a daemon that needs Postgres, a service account and a unit file, which is what the `.deb` and `.rpm` provide and an AppImage cannot.
  An AppImage of the desktop app is the Tauri shell's business (ADR 0102).
- Compression is negotiated per request.
  Hashed assets are cached by the browser indefinitely, so the cost is paid once per client per release.
  Precompressing at build time is a possible later optimization.

## Alternatives considered

**A separate `axon-web` binary.**
It would have to serve the bundle and reverse-proxy the API, including WebSocket upgrades, which is a reimplementation of the Caddy container.
The operator would run and secure two services to get one page.

**A separate package of static files, served from a configured directory.**
This keeps Node out of the server's build.
Rejected as the default because it is not one artifact: the two packages can disagree about versions, and the Homebrew formula and a bare release zip have no natural place to put a directory.
A runtime `web_root` override for an operator who wants to serve their own build remains possible later and is not needed now.

**Server-side CORS, and host the bundle anywhere.**
ADR 0046's unbuilt M-W1.5.
It does not give a native install a web client; it only removes the same-origin requirement for someone who already hosts one.

**Embed unconditionally whenever `clients/web/dist` exists.**
Rejected because the same command would then produce different binaries depending on what was left on disk.

**Ask at install whether to enable the web client.**
Rejected above.

**Configure a detected reverse proxy automatically.**
Rejected above.

**One pull request per package format.**
Rejected above.
